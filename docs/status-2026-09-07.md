# TENSELERATE on the CMP 170HX + RTX 3060 - where everything stands (2026-09-07)

One page. Every number is from the box unless marked *predicted*. The full
ledger with dates and commands is `benches/cmp170hx-3060/README.md`.

## The box

CMP 170HX, 40 GiB after the full unlock, tensor cores live (162-170 FP16
TFLOPS measured, no MMA gate on this unit), 250 W cap held at 207-223 W under
decode, HBM and SM clocks pinned at max, PCIe Gen2 x4 fused (~2 GB/s; load
time only). RTX 3060 12 GiB alongside. Model: DavidAU Qwen3.8-27B TURBO merge,
Q4_K_M, the -MTP- GGUF (16.5 GB of weights). Serving Hercules through this
fork's llama-server.

## What the numbers mean

- Batch-1 decode is 18.5 ms of weight read plus ~11 ms of GDN recurrence,
  attention and launches. The second part does not shrink with a faster
  kernel for one stream; it amortizes across width. That is why 16 streams
  give 4x the aggregate and why single-stream headroom without speculation is
  small. (The early "553 GB/s = 37%" and the later "890 GB/s = 60%" are the
  same measurement with different denominators: whole step vs. the
  width-sweep intercept.)
- Two matmul regimes: dp4a (MMVQ) costs 18.5 + 11.5 ms per extra column and
  wins up to width ~3; the tensor-core MMQ path has a ~55 ms floor from width
  2 to ~16 and wins above. The fork's `GGML_CUDA_MMVQ_MAX=N` (default 8) moves
  the crossover; 3 is the value to test with several slots.
- Speculation on this merge: depth 1 only, greedy only. llama.cpp accepts a
  draft token only when the *sampled* token equals it; temperature and
  repeat penalty destroy acceptance. Pure greedy loops in `<think>` on the
  merge, so the launch has `--sampling dry` (DRY on repeats only) and
  `--sampling low` (temp 0.3, min-p 0.1) as guards. The sweep to pick one is
  running on the box.
- The 3060 adds throughput only in parallel (a second small model for
  delegation children and compaction), never in a sequential layer split of
  the 27B: it has a quarter of the bandwidth, so every layer moved costs
  2.5x what it saves.

## What we built (repo side, all on PR #47, CI green through the merge)

- `tenselerate serve --backend llamacpp`: the measured Hercules launch in one
  command - `--jinja`, `--reasoning-format deepseek`, `--no-context-shift`,
  `--alias`, 4 slots on a unified KV pool, `--cache-reuse 256`,
  `reasoning_effort=low`, MTP depth 1 on -MTP- GGUFs, greedy sampling
  defaults, `--sampling dry|low|client`, `--mmvq-max`, `--no-mmvq`,
  `--device` (3060 pin), `--mtp-model` (retrained head sidecar). 152 tests.
- `scripts/hercules_serve.sh`, `scripts/hercules_side_serve.sh` (3060 side
  model), `HERCULES.md` (Hermes config: `temperature`/`repeat_penalty` must
  not be sent; delegation, compression, tool-output knobs).
- `GGML_CUDA_MMVQ_MAX` routing threshold in the CUDA backend (CI-compiled for
  sm_80; the 4-slot measurement is pending).
- **Upstream sync**: the fork was a snapshot with no git ancestry; merged 915
  upstream commits by three-way merge on the true base, 73 conflicts
  resolved, CPU build + 28 tests clean. Brings upstream's MMVQ speedups for
  Q4_K (*predicted* 33.5 -> ~38 single stream), 100x faster KV restore,
  and working `draft-dspark` / `draft-dflash` drafters in server mode.
  Follow-up (2026-09-08): the merge had left the fork's recurrent snapshot
  ring mixed with upstream's rollback, which broke partial `seq_rm` on GDN
  models (the MTP verify crop). All recurrent/hybrid/qwen35/context sources
  and Metal are now upstream's; the fork's own dspark model and capture API
  were dropped (upstream's `draft-dspark` covers it). Rollback tests pass.
- **GQA-packed vector attention** for quantized KV at single-token decode
  (`fattn-vec.cuh`, `GGML_CUDA_FATTN_VEC_GQA`): reads each K/V byte once per
  K/V head instead of once per Q head. *Predicted* 12.4 -> ~20 tok/s at 262K.
  Compiled by CI; not yet run.
- `scripts/mtp-head-train.py`: the head retrain (Route A) end to end, with
  `--mtp-model` to serve the result at depth 3. *Predicted* ~70 tok/s with a
  healthy head on dp4a, 85-95 with a small-width MMQ kernel.
- `benches/cmp170hx-3060/run-open-items.sh`: every unmeasured configuration
  as an unattended run on port 8089 with results appended as table rows.
- CI/release: release tarballs actually built (CPU + static CUDA sm_80/86),
  engine CI compiles ggml-cuda for sm_80 and runs every self-test; upstream's
  three new workflows dropped.

## Corrections made along the way

- 87 tok/s aggregate ceiling -> disproven at N=16 (141); replaced by the
  two-regime model.
- "MTP is dead" (7-11%) -> shallow head, depth 1 wins -> "no gain in
  production" -> it was sampling; greedy restores 46.
- ~64 tok/s for NO_MMVQ + depth 1 -> measured 30.6; MMQ has a ~55 ms floor.
- KV read ~11 ms at 262K -> measured 51; the vector kernel's per-head
  re-read, now addressed in code.
- Retrained-head target lowered from ~90 to ~70 until the MMQ floor moves.
